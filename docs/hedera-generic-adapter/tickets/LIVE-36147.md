# LIVE-36147 — [HEDERA] Add validateIntent method

- Epic: LIVE-29812 · Status: TO DO · Estimate proposed: 8 SP (largest in epic)
- https://ledgerhq.atlassian.net/browse/LIVE-36147

## Description

Implement `validateIntent` in `coin-hedera`. It is the pre-signing gate, and the framework calls it
unconditionally when computing a transaction status, so the generic path throws today.

This is a port, not a design job. `bridge/getTransactionStatus.ts` holds the behaviour to reproduce:
errors, warnings, fees, amount and total spent.

**The bar is the error keys, not the presence of errors.** Beyond the usual amount, recipient and
transaction slots, the legacy path writes four Hedera-specific keys: `stakingNodeId`,
`missingStakingNodeId`, `noRewardsToClaim` and `fee`. Only `stakingNodeId` is ever rendered on
screen — but every Hedera staking flow enables its call to action by _counting_ error keys, not by
looking at any particular one. So a key that is not reproduced does not disable a button; it
**enables a button that should have been blocked**, with nothing on screen explaining why. All four
are load-bearing even though three are never displayed.

Errors to reproduce: the four Hedera classes covering memo size, invalid staking node id (raised
twice, once with a "Validator must be set" message), redundant staking node id and no staking
rewards — plus the generic amount-required and not-enough-balance, the latter also raised with an
empty message and on the `fee` key.

## Acceptance criteria

- [ ] Transaction status works on the generic path for send, token transfer and all four staking
      flows
- [ ] Each of the four Hedera-specific error keys has its own test asserting the key on its
      triggering condition
- [ ] Amount-required and not-enough-balance are reproduced, including the `fee`-key variant
- [ ] Every staking flow's call to action is blocked under the same conditions as on the legacy path
- [ ] Existing tests that assert `validateIntent` throws are updated

**Discovered while implementing (2026-08-19), not in the ticket as filed:** `validateIntent` never
even runs for `redelegate`/`claimReward` without an additional fix. Both calls go through
`transactionToIntent` first (`generic-coin-framework/utils.ts:665`), whose default
`computeIntentType` only allows `["changeTrust","send","send-legacy","send-eip1559","stake","unstake",
"finalize_unstake"]` and throws `Unsupported transaction mode: …` for anything else — `redelegate` and
`claimReward` aren't in that list (`delegate`/`undelegate` are, via its `stake`/`unstake` remap).
Fixed by adding `computeIntentType` to `families/hedera/bridge/api.ts` (pass every generic mode
through unchanged) — this is not LIVE-36150's association mapping, it's a prerequisite for two of the
four staking modes to reach `validateIntent`/`signOperation` at all.
