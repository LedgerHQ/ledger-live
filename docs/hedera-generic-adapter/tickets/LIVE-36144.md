# LIVE-36144 — [HEDERA] Add CoinFrameworkSigner over hw-app-hedera

- Epic: LIVE-29812 [Hedera] Plug to Generic Adapter
- Status: TO DO · Estimate proposed: 3 SP
- https://ledgerhq.atlassian.net/browse/LIVE-36144

## Description

Add `families/hedera/signer.ts` so the generic coin framework can build a bridge for Hedera.

**Why this one is first.** The generic account bridge resolves the signer when it is _constructed_,
not when a transaction is signed. `getSigner` throws `No signer registered for network hedera`, and
the bridge object dereferences the signer for receive and for signing. So without this file there is
no bridge at all — account sync and receive fail too, not only signing. Nothing else in the epic can
be exercised end to end until it lands.

**No device work.** `app-hedera` is in production. There is no Device Management Kit signer for
Hedera, so this wraps `@ledgerhq/hw-app-hedera` (CLA `0xe0`) directly. Unlike EVM and Cosmos there is
no DMK-versus-legacy transport branch to copy.

Two Hedera specifics to handle:

- **Derivation asymmetry.** The wallet uses a two-level, non-hardened path, `44/3030`. The device
  derives `m/44'/3030'/0'/0'/index'` from a little-endian uint32 index carried in the APDU payload,
  so the wallet's path string never reaches it.
- `getAddress` returns a public key, not an address. That is correct for Hedera, and it is what the
  framework wants — the signing path takes the public key and puts it on the intent as the sender
  public key.

Normalise the `getAddress` options argument, or the device will ask the user to confirm their address
before every signature. `families/stellar/signer.ts` and `families/evm/signer.ts` show the shape.

One caution: the signing path calls the raw signer through an untyped context, so none of this is
checked by the compiler. Tests carry the weight here, not review.

## Acceptance criteria

- [ ] `families/hedera/signer.ts` implements the framework's signer interface and is reachable
      through the coin-module loader
- [ ] The generic account bridge for `hedera` can be constructed without throwing
- [ ] Receive returns the account's `0.0.x` address
- [ ] A signed transaction is byte-identical to one produced by the legacy path, asserted by test
- [ ] No additional on-device address confirmation is introduced during signing
- [ ] Unit tests cover the derivation-path translation

## Code notes (verified 2026-08-19)

- `libs/ledgerjs/packages/hw-app-hedera/src/Hedera.ts` exposes exactly two methods:
  - `getPublicKey(path: string): Promise<string>` — **no options argument at all**, so there is no
    `verify` flag to normalise. The ticket's "device will ask the user to confirm their address"
    caution does not apply to Hedera as the app stands today.
  - `signTransaction(transaction: Uint8Array): Promise<Uint8Array>` — **takes no path**. The index is
    hardcoded to `0` (`payload.writeUInt32LE(0)`), with a `TODO` in the source saying the BOLOS app
    supports no other index. The family signer must therefore *drop* the path the framework passes.
- The generic signing path (`bridge/generic-coin-framework/signOperation.ts:91`) calls
  `signer.signTransaction(derivationPath, unsigned, options)` — 3 args, untyped. The adapter has to
  swallow arg 1 and arg 3.
- An existing `GetAddressFn` already exists at
  `libs/coin-modules/coin-hedera/src/signer/getAddress.ts` and returns `{ path, address: publicKey,
  publicKey }`. It is reusable as-is for `CoinFrameworkSigner.getAddress`.
- Reference shape: `libs/ledger-live-common/src/families/tezos/signer.ts` (`{ context, getAddress }
  satisfies CoinFrameworkSigner`).
