# LIVE-36148 — [HEDERA] Support incremental sync in listOperations (relax minHeight)

- Epic: LIVE-29812 · Status: TO DO · Estimate proposed: 3 SP
- https://ledgerhq.atlassian.net/browse/LIVE-36148

## Description

Let `listOperations` serve a sync that is not starting from scratch.

**This one is easy to miss.** `listOperations` asserts that the minimum height is `0`. The framework
passes `0` only on a first sync; on every later sync it passes the highest known block height plus
one. So the first sync succeeds and the second throws — a smoke test passes. And because it is an
assertion rather than a "not supported" stub, it does not appear when you grep for unimplemented
methods.

Underneath is a modelling difference, not an oversight. Hedera has no global chain of blocks, so the
module falls back to a synthetic constant block height of `10` for operations that carry none. A
synced account therefore stores block height `10`, and the next sync asks for `11`.

Reproducing it needs no chain state: a stored account with a block height and a sync hash is enough.
Make that a regression test.

While in here, check the assertion that an EVM address resolves, on the same path.

## Acceptance criteria

- [ ] A second sync of a stored Hedera account completes without throwing
- [ ] Operations are neither duplicated nor lost across consecutive syncs
- [ ] A test drives two syncs in a row and asserts the resulting operation list
- [ ] Existing tests that assert the minimum-height rejection are updated

## Code notes (verified 2026-08-19)

- The assertion: `libs/coin-modules/coin-hedera/src/api/index.ts:127`
  `invariant(minHeight === 0, "minHeight is not supported");`
- The EVM-address assertion on the same path: `api/index.ts:134`
  `invariant(evmAddress, "hedera: evm address is missing for …")` — a throw, so it fails the whole
  sync rather than degrading.
- `HARDCODED_BLOCK_HEIGHT` lives in `libs/coin-modules/coin-hedera/src/constants.ts` and is written
  to the account at `bridge/synchronisation.ts:140`.
- Tests pinning the current behaviour: `api/index.test.ts:324-327`.
- Note the incremental cursor for Hedera is really a **consensus timestamp**, not a height — the
  legacy `getAccountShape` already does it that way (`bridge/synchronisation.ts:66-72`). The likely
  fix is to accept any `minHeight` and keep paging on the timestamp cursor the framework supplies.
