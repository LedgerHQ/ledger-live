# LIVE-36149 — [HEDERA] Close residual API gaps: max-send, balance options, supportedFeatures

- Epic: LIVE-29812 · Status: TO DO · Estimate proposed: 3 SP
- https://ledgerhq.atlassian.net/browse/LIVE-36149

## Description

Three small, independent items on `coin-hedera`'s API surface.

1. `craftTransaction` rejects "use all amount", so there is no max-send. Implement it. This is
   independent of the transaction-status work: the framework's max-spendable path calls fee
   estimation only and never `validateIntent`. Note Hedera's fee schedule applies two safety
   multipliers, so the inflated figure is what a max-send reserves.
2. `getBalance` throws if any options are passed. Harmless today, but the family bridge api added
   alongside this epic is exactly what could start supplying them. Decide deliberately: either
   support the options, or keep rejecting them and leave the balance options unset.
3. `supportedFeatures` declares `send` only, although staking and token operations are implemented.
   The generic framework never reads it, so this is not a migration blocker — but the monitoring
   package and the coin service do read it, and are being told the wrong thing.

## Acceptance criteria

- [ ] A max-send transaction can be crafted, signed and broadcast, with fees correctly reserved
- [ ] The balance-options behaviour is settled and consistent with what the family bridge api supplies
- [ ] `supportedFeatures` declares the operations the module actually implements
- [ ] Existing tests asserting the two rejections are updated
