# LIVE-36150 — [HEDERA] Route token association through changeTrust and verify CAL namespaces

- Epic: LIVE-29812 · Status: TO DO · Estimate proposed: 3 SP
- https://ledgerhq.atlassian.net/browse/LIVE-36150

## Description

Make token association expressible on the generic path, and confirm the asset registry can serve both
of Hedera's token standards.

### Association

Hedera requires a separate association transaction before an account can hold a token, and it is the
most expensive operation in the fee schedule — so it must be a first-class mode, never a silent send.

The generic transaction mode list has no association member, but it does have `changeTrust`, which
the framework already maps to an opt-in operation type, and account sync already recognises opt-in
and opt-out operations. **Reuse `changeTrust`** and route Hedera's association through the family's
own intent-type hook. Do not extend the shared mode list. Stellar does the same for its trustlines.

### Registry check

Hedera carries two token standards under one currency: HTS tokens referenced as `0.0.x`, and ERC-20
tokens on the Hedera EVM referenced as `0x` addresses. The framework resolves a token from an asset
by reference alone and does not compare standards. The two formats cannot collide, and the module
already tags every token operation with its standard, so this is expected to need no change. Confirm
it against the registry rather than assuming — a collision here is the one thing that would force a
shared-layer change.

## Acceptance criteria

- [ ] An association transaction can be crafted, signed and broadcast on the generic path
- [ ] It appears as an opt-in operation in history
- [ ] Sending and receiving an HTS token and an ERC-20 token both work, each resolving to the correct
      token
- [ ] The shared transaction mode list is unchanged
- [ ] Registry resolution for both reference formats is confirmed, and the result recorded on this
      ticket

## Registry check — result (2026-08-19)

`getCryptoAssetsStore().findTokenByAddressInCurrency(address, currencyId)`
(`features/platform/currencies/src/legacy/store/buildCryptoAssetsStore.ts:68`) is a thin passthrough
to a remote RTK-Query call (`findTokenByAddressInCurrency.initiate({contract_address: address,
network: currencyId})`) — **no local normalization, case-folding or numeric parsing** happens in this
codebase before the lookup. Hedera's own callers (`families/hedera/bridge/api.ts`'s
`getTokenFromAsset`, and coin-hedera's identical legacy version) pass the reference through verbatim:
`0.0.x` for HTS, `0x…` for ERC-20. The two formats are lexically disjoint under any string-equality or
prefix-based index, so **no client-side collision is possible**.

What this repo's tests cannot verify: whether the CAL backend itself applies any cross-format
normalization server-side — that's outside this codebase, and this sandbox has no network access to
query it. Recorded as: **client-side resolution confirmed safe; recommend a manual CAL query in
staging as the actual end-to-end verification**, not a code-level one.
