Fail `agent-intent enroll` with `keychain_unavailable` when Linux has no Secret Service, and add `--allow-plaintext-key` to store the agent key in a 0600 file after the human agrees. When a Secret Service is reachable but refuses the write (e.g. a locked collection), `enroll` also fails with `keychain_unavailable` and the write error, or, with `--allow-plaintext-key`, stores the key in the file and says so on stderr. Each profile records its `keyStore` (`os-keychain` or `plaintext-file`), shown by `agent-intent show` and in the `list`/`show` JSON. Older wallet-cli versions don't know `plaintext-file` profiles and drop `keyStore` when they rewrite the session file. On Linux, Agent Intent and Ledger API auth keychain entries are pinned to the Secret Service, so they never fall back to the kernel keyring. Existing Agent Intent profiles read on Linux without a reachable Secret Service now fail with `keychain_unavailable`, asking to make it reachable and re-run; only a profile an older wallet-cli enrolled without one (whose key went to the kernel keyring) is gone and must be re-enrolled under a new `--profile` id (with `--allow-plaintext-key` only after the human agrees). A keychain read error that may be transient asks to unlock the OS keychain, and a failed delete of a keychain entry (e.g. on `ring destroy` or an enroll rollback) is now reported instead of being taken as success. Swap quote requests no longer use a throwaway API key when the OS keychain is missing or can't save it: they are sent without a token, with a warning on stderr.
