# @features/platform-predictions

> [!CAUTION]
> **Status: UNSTABLE** — New package; the Predictions onboarding contract may still change.

Wallet API custom handlers (`custom.predictions.*`) that let the Predictions live app open Ledger Wallet's native onboarding sheet (intro, terms and consent steps), its "Confirm account ownership" prompt and its buy order signing sheet.

## How it works

The live app calls `custom.predictions.onboard` with the documents it needs the user to accept, e.g. `{ intro: {}, terms: { termsVersion, disclaimerVersion }, consent: { disclosureVersion } }` or only `{ terms }` once the terms change. Ledger Wallet shows the requested steps in one sheet, always in the intro, terms, consent order and skipping an intro the user already saw, then answers with the accepted versions: `{ isCompleted, terms?, consent? }`. A version Ledger Wallet has no text for is refused with `UnsupportedOnboardingVersion` before anything opens. `custom.predictions.close` closes the sheet and the live app.

`handlers({ uiHooks })` returns the handlers to merge into a live app player's custom handlers. Each app implements `PredictionsUiHooks`:

- `sheet.open(sheet, onCancel)` shows a `PredictionsSheet`; `sheet.onStepAccept` runs as each step is accepted, `sheet.onComplete` once the last one is, `onCancel` when the sheet closes before the last step (dismissed, closed or replaced by another one)
- `sheet.close` and `app.close` close the sheet and the live app
- `intro.isSeen` and `intro.markSeen` read and set the persisted "intro seen" flag
- `binding.sign(accountId)` shows the "Confirm account ownership" prompt and signs the binding message with the account, and `binding.reportSetup(setup)` shows how the trading wallet setup ended, see below
- `order.sign(accountId, typedData)` shows the "Continue on your <device>" prompt and signs the checked order with the account, and `order.report(walletOrderId, status)` shows how the order ended and answers `close` or `retry`, see below

A sheet that closes before the last step (dismissed, replaced or closed) answers `isCompleted: false` with the versions accepted until then, so the live app can store them and resume after them. Invalid params, including an unknown document, reject with `INVALID_PARAMS`.

`PREDICTIONS_LIVE_APP_ID` is the default manifest id of the Predictions live app, used when the `ptxPredictionsLiveAppDesktop` or `ptxPredictionsLiveAppMobile` flag sets none.

`getPredictionsWebviewInputs(linkParams, hostInputs)` builds the inputs of the Predictions screen's webview: the deep link's params (e.g. `eventSlug`), then the host context (theme, platform, …), which a link param can't override. A `goToURL` gets them in its query too, since Ledger Wallet loads a whitelisted `goToURL` as is.

## Account binding

Before the live app creates the user's trading wallet, it calls `custom.predictions.bindAccount` with `{ accountId }`, the Wallet API id of the account the user picked. Ledger Wallet signs an EIP-712 message with it on the device, which proves the user controls that account, and answers `{ typedData, signature }`. The live app checks the signature recovers to the account; it never sends it to the provider.

- The message (`getBindingTypedData`) is built here, never by the live app, so this prompt can only sign it. The device shows `ConfirmAccountOwnership`: an action, the account and the delegation notice. It isn't clear-signed yet (no descriptor), so the Ethereum app needs blind signing.
- The signature runs as a Device Intent (`predictionsSigningIntentDefinition`, in `src/signingIntent/`), shared by every Predictions signature: the job signs the request's typed data with the host-injected `signTypedData`, checks the signer (`isTypedDataSigner`) and reports a `signed` or `mismatch` result through `onResult`. The request's `purpose` (`binding` or `order`) picks, in `SIGNING_PURPOSES`, the only `primaryType` its prompt signs (`createPredictionsSigner` rejects any other with a `ZodError`, so `INVALID_PARAMS`), the device error label and the mismatch error. Each app adds its renderer and mounts it in its Device Intent Executor, which shows the connection and the Ethereum app; the renderer shows the purpose's prompt from its `predictions.<purpose>.*` keys ("Confirm account ownership on your <device>" for the binding) and keeps it from closing while the device waits. A device error (refusal, blind signing disabled, disconnection…) is a state with a retry; a signature from another key is `mismatch`.
- The app implements `binding.sign` with `createPredictionsSigner` (`src/signingRequests.ts`), one per live app player and purpose, which opens the signature on the app's mounted root through its `createSigningRequests`, settles once with the first answer (`{ typedData, signature }`), and cancels only the request it opened. The app injects what needs legacy code: finding the account (its own `findPredictionsAccount`, which throws `PredictionsAccountNotFound` for an unknown or non-EVM account), the typed data to sign for it (`getBindingTypedData` of its address), the refusal (`UserRefusedOnDevice`) and what runs once signed (opening the setup). Its root opens the executor, signing with its own `signPredictionsTypedData` on the executor's DMK session (live-common's `runSignTypedDataEvm`, which cancels the device action when the executor stops). Once signed, the executor closes, the trading wallet setup of `@features/flow-predictions` opens on "Setting up your trading account", and `binding.sign` answers, so the live app sets up the wallet behind it.
- The live app then calls `custom.predictions.reportSetup` with `{ outcome: "created" | "found" }` or `{ outcome: "failed", reason }` (`failed-deploy`, `failed-permission`, `timeout`, `unavailable`, `unknown`). The app implements `binding.reportSetup` with `usePredictionsSetupHooks` of `@features/flow-predictions`, which shows that outcome and answers once the user closes it, so the live app shows what's behind only then. With no setup open, it answers right away. Closing the live app cancels its open binding and closes its setup.
- Closing the prompt before signing answers `UserRefusedOnDevice`. A signature from another key answers `PredictionsBindingSignerMismatch` right away. Invalid params reject with `INVALID_PARAMS`.

## Buy orders

The buy flow has no review screen in the live app: once the user confirms, it calls `custom.predictions.signOrder` with `{ accountId, typedData }`, `typedData` being the EIP-712 JSON string of the order authorization MoonPay executes (`BoxPolymarketPlaceOrder`). Ledger Wallet signs it on the device and answers `{ signature, walletOrderId }`, Ledger Wallet's id for the open order (not Polymarket's order id).

- `typedData` must be exactly that authorization (`placeOrderTypedDataJsonSchema`, `src/placeOrderTypedData.ts`): domain `{ name: "BoxPolymarketPlaceOrder", version: "1", chainId: 137 }` without a verifying contract, primary type `PlaceOrder`, the domain and `PlaceOrder` fields in MoonPay's order, and a message with exactly those values: a `BUY` of type `FOK` (the only order the sheet describes), uint256 values that fit in 256 bits, expiring within the next 300 s (the message has no nonce, so the expiration is what keeps a signature from being replayed later). Anything else rejects with `INVALID_PARAMS` before anything opens, so this prompt can't sign arbitrary data. The expiration is checked again before each attempt on the device: a retry or a reconnect after the order expired closes the prompt unsigned and rejects with `PredictionsOrderExpired`, so the live app quotes again.
- The signature runs through the same signing intent as the binding, with the `order` purpose: the "Continue on your <device>" prompt, device errors with a retry, and the signer check. The app implements `order.sign` with its own `createPredictionsSigner`, which signs the checked typed data; once `sign()` resolves, the handler opens the order sheet of `@features/flow-predictions` on "Placing your order" with `startOrder()`.
- Closing the prompt before signing answers `UserRefusedOnDevice`, a signature from another key `PredictionsOrderSignerMismatch`, and an unknown or non-EVM account `PredictionsAccountNotFound`.
- Once the order settles, the live app calls `custom.predictions.reportOrder` with the `walletOrderId` it got and the order's status, e.g. `{ walletOrderId, status: "filled", shares, price }` (or `{ status: "filled" }` when the fill isn't known), `{ status: "not-filled" }`, `{ status: "rejected", reason }` (`expired-signature`, `insufficient-balance`, `invalid-tick-size`, `market-closed`, `not-accepted`) or `{ status: "unconfirmed" }`. The app implements `order.report` with `usePredictionsOrderHooks` of `@features/flow-predictions`, which shows it in the same sheet and answers `{ action: "close" | "retry" }` once the user closes it or tries again. When `walletOrderId` isn't the order this player has open (none, or one that timed out or a newer order replaced), it answers `close` right away and leaves the sheet as it is. When the live app doesn't report within 3 minutes, the sheet shows the `unconfirmed` status and a later report answers `close` right away. Closing the live app cancels its open order signature and closes its order.
