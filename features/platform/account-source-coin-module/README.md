# @features/platform-account-source-coin-module

> [!CAUTION]
> **Status: UNSTABLE.** API may change while the coin module kinds plug in.

An [`AccountDataSource`](../../../domain/api/account-data) that reads coin modules directly, without the `generic-coin-framework` layer. It serves the `balance`, `operations` and `accountStatus` kinds.

- `createCoinModuleSource(host)`: the source, id `coin-module`.
  - `supports`: a descriptor whose network's currency has a registered coin module. No family list: the registry decides, so a currency without a coin module falls through to the next ranked source. A `utxo` descriptor is served only where the host says the coin module reads an xpub (`readsXpub`): none does today, since they read one address, so utxo accounts stay with FullSync.
  - `balance`: reads the coin module by the account's address, or its xpub for a `utxo` descriptor, and answers the account's native coin first, then its listed, non-blacklisted tokens. A native `spendableBalance` is `value - locked`.
    - `read.balance` reads one account. There is no batch reader: a coin module reads one address per call, so the router limits and settles the accounts itself.
    - An account the coin module cannot answer completely falls through to the next source (`AccountDataNotServedError`): no balance read in the coin module (`getApi` resolves `undefined`), or tokens returned with no token resolver to list them.
  - `operations`: served only where the host says the coin module pages its operations (`paginatesOperations`), so any other currency falls through to the next source. A read walks `listOperations` pages, newest first, from the target's `cursor` with the query's `limit`, until `limit` operations are listed (one without a limit), the list ends, or `MAX_PAGES_PER_READ` pages are read: a page its filters emptied does not end the list. A `filterAsset` query keeps the rows of that asset only: the coin module lists every asset, so the source filters them, and counts only the asset's rows towards `limit`, a `FEES` row included. The rows are built from every asset first, so a token row still points at its transaction's native operation. The module's last `next` is the page's `nextCursor`, absent at the end of the list or when it does not advance.
    - Token and internal operations are rows of their own, pointing at their transaction's native operation. A coin module may list no native operation for a transaction that only moved tokens: when the account paid its fees (`feesPayer`), a `FEES` row carries them and the token rows point at it, as the legacy sync shows them. Only the parent row carries the fee.
    - NFT transfers, failed incoming transfers, unlisted and blacklisted tokens are left out, as the legacy sync does. Tokens with no token resolver make the read fall through on a first page, and fail a next page.
    - Pending operations are not listed: a coin module lists mined transactions only. The app host serves no operations until they are (`servesOperations`), so FullSync answers them.
  - `accountStatus`: asks the coin module's `getAccountStatus` (coin-modules [ADR-079](https://github.com/LedgerHQ/coin-modules/pull/1292), declared by each module until the framework has it) with the descriptor key as is: an address, or the public key of a family keyed on it, since an account still to onboard has no address. The module answers facts, `used` and, where the chain has one, `isOnboarded`; the source makes the gate of them: `onboarding` when `isOnboarded` is false. A module without it falls through to the next source. TON, Canton and Concordium implement it.
- `CoinModuleHost`: what the source takes from the coin modules (`isCurrencySupported`, `getApi`, `paginatesOperations`, `getOperationsApi`, `getAccountStatusApi`, `blacklistedTokenIds`). The package cannot import `libs/`, so the app injects it: `createCoinModuleHost` in `@ledgerhq/live-common/account-data/coin-module/createCoinModuleHost` builds it on the coin module registry, with no `generic-coin-framework` layer. It serves the currencies whose family loader supports them and ships a local api. With `servesOperations`, operations are paged for a family the generic bridge sends a `limit` to, as listed in the code: the remote config only tunes the page size, also the most a page asks for.

Each app ranks it before the FullSync source in `src/config/account-data-setup.ts`, so FullSync stays the fallback. See [the account data layer](../../../docs/account-models/data-layer.md).
